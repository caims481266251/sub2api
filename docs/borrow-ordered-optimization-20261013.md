# 借票问题按优先级优化与证据复核

日期：2026-10-13。基线提交：`0821a9015`。

本轮先修复已确认的业务错误观测缺口和租约释放失败处理，再补足候选选择、同路由质量和阶段耗时的证据。没有新增探测策略开关，也没有修改账号身份、额度、并发、冷却、路由接单窗口、推理级别或线上/本地运行配置。

## 1. 业务错误与租约释放

### 已确认的缺陷

`handleStreamingResponseWithReasoning` 在已输出内容后遇到 HTTP/2 读错误，会自行写出错误事件并将响应标记为已提交。这个分支此前未调用 `MarkOpsStreamFailure`，handler 又不会再补写错误。错误日志可能只得到响应文本，丢失实际借票路由和出站时序；语义上的 502 也容易混作真实上游 HTTP 状态。

现在这个分支登记运维快照，保留错误分类、实际账号、路由、模型、推理、出站尝试和真实 HTTP 状态。真实 HTTP 200 上发生的流错误仍按请求失败处理，错误的语义状态可为 502，二者分别记录。响应内容和业务恢复规则没有修改。

解析器标记错误可能早于 deferred body/lease cleanup。HTTP 运维日志最终读取时按原尝试编号刷新该尝试的结束状态，不把后一次重试的路由套到前一次错误，也不修改已经返回的快照；WebSocket 每轮快照保持原处理。

### 租约释放

此前 `ReleaseRoute` 的错误被直接忽略。现在保留原有总共 3 秒的清理预算，最多执行两次幂等 DELETE，每次最多 1.5 秒。成功停止；两次失败则明确记录失败，继续依靠原租约 TTL 兜底，不续租已结束请求，不将释放重试变成业务重试。

请求时序增加租约哈希、结束原因、释放状态和释放次数。日志中的 trace ID 和租约哈希可以关联成功、失败、EOF、关闭及取消路径，不记录原始租约标识、Cookie、票据或代理凭据。完成响应后若数据库临时异常，可以通过第二次删除及时释放占用。

上轮“5 个客户端、采样 6 个业务租约”的根因仍未被历史记录证明。本轮修复的是可确认的“释放失败被忽略且不可追踪”，不能将它写成已证实的额外租约根因。正常流跨过路由接单截止后仍然自然结束；没有缩短租约或按路由年龄取消业务。

## 2. 候选网关重复与选择机制

复核了已有 `borrow-pool-priority-validation-20261013.md`：原排序和“未用网关优先”均为 9/58，不支持再次直接上线“成功过的网关一律降级”。当前代码已经按目标及配置代次记录确定失败，短暂降低近期重复失败网关的优先级；成功可解除降级，只有降级候选时仍会回退验证。

本轮没有叠加第二套排序。自身流水线与来源共享池均增加每次实际选取时的 `gateway_selection`：

| 字段 | 含义 |
| --- | --- |
| eligible | 进入当前排序集合的候选数量；自身队列后续仍需通过有效期及库存准入检查，共享池先过滤领取条件 |
| gateways | 其中已知网关名称的去重数，未知网关不虚构为新网关 |
| deprioritized | 其中受近期失败反馈影响而降级的候选数 |

结合已有 `gateway_priority=normal/prioritized/recheck`，可以区分没有其他网关、排序确实让位、必须回退复查。共享池统计和领取在同一事务、同一合格候选集合完成，不将过期或剩余时间不足的候选计入可选集合。不会把池容量 64 当作必须填满的库存目标。

## 3. 路由回答质量

新增只读工具 `scripts/analyze-borrow-evidence.py`，按实际出站归属聚合相同路由、模型、推理级别和题型，保留请求编号、发出时路由年龄、接单剩余、首字和答案判定。失败若没有 usage 记录，使用同 request trace 的运维尝试补充；派发前看到的路由不能代替真实归属，多路恢复的结果也不强行分配给某一条路由。

历史回放准确保留 79 正确、2 错答、4 失败，以及请求 35、79 的实际路由缺失。相同路由/模型/推理/题型中仍能找到请求 57 正确、67 错误这一组。没有据此设置“30 秒过期”或禁用 low；只有一个相关窗口，无法分离年龄、当时负载和上游随机性。

下一次真实质量验证采用同路由内的配对：固定糖果题与模型，在不同路由年龄重复发送，同时交错 low/medium 并记录在途数；正确性、证明审计与格式遵从分开。接单截止仅控制新请求，已发送请求完整排空。判据看同路由内差异及跨多个独立窗口的可复现性，不把窗口内样本当作完全独立样本。

## 4. 滚动补充

继续使用当前全局滚动补充开关，不增加新的预热机制。上一轮只覆盖关闭状态，因此没有充分数据宣称开启一定改善质量或稳定性。本轮完成现有逻辑回归，实际开关未更改。

后续验证协议为交错顺序的等长开/关窗口，保持目标身份、模型分布、业务并发、请求预算及接单窗口一致，区分切换后的旧候选过渡。主要指标：无可接单路由秒数、最长空窗、可用路由每分钟产出、每百次目标 HTTP 的有效路由产出、每条路由正确业务产出及新增来源请求成本。质量和容量同时评估；仅增加候选和请求数不算改善。

## 5. 探测耗时拆分

上述工具直接利用已经存在的阶段事件，将槽位等待、数据库准入、连接准备、响应头等待和响应体阶段分开。缺失阶段事件保持未知；正常取消单列，目标/候选终结判定与 HTTP 阶段计数分开。

对上一轮最终不可变快照的回放结果如下。这是 HTTP 阶段样本，不能与 69 条唯一目标判定混为同一分母。

| 非正常取消阶段 | 样本数 | 槽位等待中位数 | 数据库准入中位数 | 连接准备中位数 | 请求写完至响应头中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| mint | 71 | 4.260 秒 | 8 毫秒 | 0.919 秒（71） | 1.101 秒（71） |
| continue | 58 | 3.552 秒 | 7.5 毫秒 | 0.941 秒（57） | 1.057 秒（57） |

mint 响应体阶段中位数 7.255 秒；continue 为 3 毫秒，后者包含大量在响应头已确定换票后快速结束的失败。各列中位数不能相加当作整体中位数。对比时必须区分通过、确定失败、不确定和正常取消；没有依据将这些等待统一归因于 503，或直接缩短业务超时。

后续若验证槽位调度优化，应单独比较“来源预取是否占据了目标即将需要的槽位”，继续保持目标总后台并发上限，并比较空闲率与路由产出。现有续接优先级已存在，没有依据为此扩大并发或另加固定保留槽。
