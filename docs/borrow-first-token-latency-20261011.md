# 真实借票业务首字延迟定位（2026-10-11）

结论：本轮可见答案首字的主要耗时发生在**请求已发往上游网关并收到响应头之后，等待答案内容产生/传回的阶段**。本地账号调度、并发排队和最后的转发刷新没有形成秒级瓶颈。

样本来自 `borrow-priority-live-20261011-163600`，gpt-6-astra/medium，每目标最多5并发。80条糖果题中74条完整完成、5条90秒截断、1条上游502。下表仅统计74条具有完整服务端 request_timing_details 和客户端 delta 时间的回答；不将截断样本当完整首字分布，也不把短句OK校验混进糖果题。

## 页面“首字”与可见答案不同

当前流式处理保留原有 `semantic` TTFT 口径：跳过 response.created/in_progress 等元信息后，第一个语义事件即可开始计时。例如 reasoning 类型的 output_item 事件可以早于答案文字。

代码依据：`backend/internal/service/openai_gateway_passthrough.go:1332` 的 `openAIStreamDataStartsSemanticTTFT`；可见事件判定在同文件1289行。`backend/internal/service/openai_gateway_response_handling.go:724` 先记录上游输出，再刷新；首个可见token尽快flush的逻辑在728行。本轮SSE没有reasoning文本delta，可见首字与客户端第一个 `response.output_text.delta` 对应；一般场景的first_visible也可包含推理文本等，并不永久等于最终答案正文。

页面 first_token_ms 还从业务转发起点计时，服务端 first_semantic 从请求入口计时，两者通常相差几十毫秒。这不改变本轮10秒分组。

## 能定位到什么程度

这些证据把瓶颈定位到**上游输出等待段**。上游网关自身排队、模型内部推理、上游缓冲、代理链路中的响应体交付都可能包含在其中，现有事件无法把它们进一步独立拆开。虽然完成响应有reasoning tokens（中位516）和medium标记，但不能把整段等待都称为模型思考，也不能断言全部是代理问题。

若下一步继续定位，最有价值的是在真实HTTP传输层增加响应体首批字节、首个SSE元事件、首个reasoning事件和首个答案delta时间，并与上游请求ID对齐。现有first_byte主要是HTTP首响应字节（接近headers），不足以确定SSE正文何时开始。此为后续建议，本轮没有修改推理强度、模型或业务超时。
