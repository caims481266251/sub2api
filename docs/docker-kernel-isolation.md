# 容器账号隔离与持久身份

## 实现边界

每个 `docker_kernel` 账号绑定一个持久实例、一套独立目录和 Docker bridge 网络。Sub2API 原有调度、用户/API Key/账号并发、计费和业务错误处理保持原逻辑。本改动不新增请求并发上限，不改变 CPU 配额，也不把上游错误作为容器隔离故障。

Docker 共享宿主机内核；不同内网 IP、MAC、machine-id 不代表不同公网 IP 或 TLS 指纹。只读镜像和内核程序可以共享，可写账号状态不可共享。当前固定内核只支持 Codex/OpenAI。

## 生命周期约束

- 创建先持久化账号绑定、机器身份和设备身份，再预留网络、创建容器；失败重试复用已保存身份和租约。
- 重启、凭据刷新、401 重新授权、保留实例目录的容器重建不生成新身份。
- 已投影凭据或已有容器的实例丢失 `device_id` 时返回 `client_identity_missing`，禁止静默换设备。
- 同账号出现多个 manifest 时返回 `account_binding_conflict`。manifest 的实例 ID 必须匹配目录名，机器身份必须符合生成格式。
- 删除仍沿用原流程：确认容器和网络已移除后才释放租约；外部操作结果不明确时保留资源记录。

## 就绪检查

helper 从 Docker inspect 校验实际状态，不能仅凭标签接管容器：

1. 只连接账号分配的网络；核对 IP、MAC 和 network ID；拒绝网络内的其他容器。
2. 只允许本实例 `home`、`run`、`credentials`、hosts、machine-id 和固定只读 payload 挂载；拒绝额外挂载、可写凭据和共享挂载传播。
3. 根文件系统只读、非 privileged、不共享 PID/IPC/UTS；拒绝额外设备、公开端口和弱化安全配置。
4. 启动阶段 capabilities 仅保留现有必要集合；必须启用 no-new-privileges；临时文件系统符合固定策略。
5. 容器内检查 PID 1 的 UID/GID、所有 capability 集合和 NoNewPrivs；核对 hostname、machine-id、内核配置中的实例 ID、device_id、凭据路径与强制代理设置。
6. 内核健康接口必须回报与配置一致的 `vm_id`、`device_id`。这证明内核已加载身份，不等于上游 HTTP/TLS 指纹已经验收。

这些检查在生命周期和健康检查控制面执行，不增加每个模型请求的 Docker 调用。普通代理、401、429 和模型错误继续沿用业务错误处理。

旧实例若不符合这些不变量会被拒绝准入；不会为了通过校验自动换身份、删数据或放松权限。修复需恢复该实例的正确配置。共享 Docker daemon 的管理员仍具有控制所有容器的权限，以上不构成针对宿主 root 的安全边界。

## 2FA 重新授权

任务队列在领取前将容器账号定向到本地 Worker，避免全局 Session Studio 设置导致任务一直等待。容器模式账号使用本地登录 Worker 和账号当前绑定代理，不使用通用登录配置中的其他代理池；代理缺失/无效时任务失败，不回退直连。普通账号保持原有可选引擎与代理策略。

密码/TOTP 登录子进程每任务拥有独立 HOME、XDG 配置/缓存/数据/状态目录及临时目录，任务结束清理。清除继承的 HTTP(S)/ALL/NO_PROXY 和通用登录代理/端点覆盖变量，代理由任务参数提供；不传递 Worker Token。

既有账号身份匹配、凭据摘要检查和原子条件更新继续阻止过期任务覆盖新凭据。持久 2FA 加密记录和恢复日志不属于临时登录目录，不清理。

## 验证与证据边界

- Go 运行时回归与竞态检测：持久身份、重复绑定、配置篡改、跨账号挂载、权限变化、MAC 和网络成员冲突、失败恢复。
- 可选真实 Docker 测试 `TestDockerLiveIsolatedAllocationAndRestart`：两个临时容器、独立网络/临时文件、停止/启动、错误挂网、外来网络成员、另一实例持续运行、归属限定清理。使用惰性进程，不访问模型提供商。
- Python 单元测试：进程权限、身份回报、账号配置、代理桥和登录子进程环境。
- 隔离 PostgreSQL 实测：直接执行当前任务领取 SQL；全局 Session Studio 下容器任务由本地 Worker 领取，普通账号任务仍由 Session Studio 领取，测试数据库容器已移除。
- 服务层定向回归：容器重新授权使用账号代理、缺失代理拒绝、普通模式配置兼容、401 恢复。
- 本轮对当前运行内核进行只读核验，确认其健康接口包含匹配的设备/实例身份，且进程权限和机器标识符合新增检查。

2026-10-24 本地真实双账号补充验收：两个不同上游账号已通过登录/加密登记与实际隔离检查；混合业务请求 66/68 成功，另外两次为账号 A 上游限额拒绝。实测每账号峰值 15、合计 30 在途。账号 B 在 15 在途时注入真实 401，自动重新授权后恢复阶段 15/15 成功，持久身份不变。详细证据保留在 `.dev/docker-kernel/verification/isolation-two-accounts-20261024/README.md`。

容器健康 `ready` 与管理员 `schedulable` 开关不能作为重新授权恢复完成的依据。登录凭据落库之后，控制面仍需把新凭据装入内核；该窗口请求可能返回 503。验收需以真实业务成功判定恢复，本次约 152 秒完成首个恢复请求。首次过早执行的失败报告保留，不将其抹去。

两个账号使用同一代理，公网出口实测相同；未验收公网出口唯一性或不同 TLS 指纹。不要用重复导入同一个上游账户代替不同上游账户的额度隔离验收。

## 发布要求

部署本改动需同步包含主程序、helper、Docker runtime 镜像（common.py/observe）和重新授权 Worker；只更新主程序不会更新容器内检查脚本。沿用现有版本打包与 updater，保留实例目录和身份，不需要数据库迁移。新版本发布和部署应核对运行镜像与源码版本。
