## 账号创建与数量

`GET /api/v1/admin/accounts/docker-system-pool` 使用账号管理权限，返回：

```json
{
  "profiles": [
    {
      "profile_id": "ubuntu-24.04",
      "display_name": "Ubuntu 24.04 LTS",
      "available": true,
      "unavailable_reason": "",
      "bound_account_count": 12
    }
  ],
  "legacy_bound_account_count": 3,
  "checked_at": "2026-10-27T10:00:00Z",
  "count_scope": "all"
}
```

示例数字仅说明接口形状。实际返回全部五项，HTTP 响应仍使用项目标准 `data` 包装。受限观察者返回可见分组统计与 `count_scope: visible`，不暴露全局账号数。

创建请求中的 `docker_system_profile` 接受 `auto` 或上述系统 ID。Docker 创建省略时为 `auto`；普通模式不提交，服务端拒绝普通账号指定系统。OAuth、2FA / Session、批量创建和数据导入的新建分支已透传。导入命中已有账号时保留原绑定。导出记录携带实际系统，导入生成新账号时作为指定系统处理；旧空绑定导入生成的新账号正常自动分配。

实际分配经过以下路径：

```text
创建请求 → 本地已验证目录校验 → 创建事务取得 PostgreSQL advisory xact lock
       → 聚合未软删除 Docker 账号 → 选最少绑定系统 → 插入账号并提交
       → 现有初始化读取实际绑定 → 精确模板创建容器 → 常驻内核 → 原业务调度
```

数量包含初始化中、异常和停用账号，不等于运行容器数。事务失败不增加数量，软删除后不计数。相同数量按固定系统顺序选择；手动选择也经过相同事务。分配使用全局数量，受限页面的显示数量仅为其可见范围。

迁移 `312_account_docker_system_profile.sql` 只增加 nullable 字段、约束、部分索引和不可变触发器，不回填已有数据。字段不存于 `extra`，不接受镜像地址、摘要、宿主路径或命令。数据库禁止旧空绑定改为新系统以及已保存绑定改写。调度缓存完整保留该只读字段。

## 安装、更新与回滚

1. 原生 amd64 / ARM64 runner 构建对应镜像，禁止通过跨架构 nft 模拟结果认定可用。打包脚本保存全部镜像，输出 `manifest_version: 2` / `minimum_updater: 2` 的清单及校验和。
2. 旧宿主更新器需先安装同版本、同架构的 `docker-kernel-updater-bootstrap-VERSION-linux-ARCH.tar.gz`。解压后执行其中 `deploy/docker-kernel/host/install-update-agent.py`，使用该主机原有路径和服务 UID / GID；安装器显式重启 updater。不能只在线替换主程序就宣称系统池已安装。
3. 主程序先检查 updater 的 `/v1/capabilities`。旧版本明确报需升级宿主组件，不能解释新多镜像包。
4. `prepare` 下载并校验整包、逐镜像摘要 / 架构 / 系统依赖及固定 payload，完成 nft 和内核健康检查；账号初始化只使用本地已安装镜像。
5. `activate` 取得现有协调锁后，按系统标识更新各自映射。未包含的自定义模板保持原样；单纯增加系统池且入口脚本未变时，保留原 `default` 镜像。若同时发布入口程序修复（例如本轮移除 UA 覆写），先核对新旧默认镜像的真实系统 ID / 版本相同，再执行原有维护窗口内的兼容镜像更新。系统不符则明确拒绝升级。旧账号仍为空绑定 / `default`，不进入系统池。
6. 激活日志保留完整 templates、systemd unit 和 active 元数据。失败或异常中断恢复原映射；镜像缺失不得静默改用其他系统。清理保护当前版本、必要回滚版本及仍被模板 / 容器引用的镜像，只清本项目受管理产物。

首装可使用 `--payload-dir`、`--version` 和需要时的 `--activate`；已有模板不得使用新 payload 参数覆盖。私有固定内核不进入公开包，仍由宿主现有可信 payload 提供。发布源使用已提交的快照；本轮临时验证镜像不能作为正式发布产物。
